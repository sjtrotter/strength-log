# Release build & signing

Steps for cutting a signed release build of `:app`. This is a public repo
(CLAUDE.md data principles) — the signing key never enters it, in any form.
These steps are user-run; an agent has no signing key and shouldn't.

## 1. One-time: create the release keystore

Do this once, on your own machine, and keep the resulting file somewhere
that isn't this repo (a password manager's attachment, an encrypted volume,
whatever you'd trust with a house key):

```
keytool -genkeypair -v \
  -keystore ~/keystores/strength-log-release.jks \
  -alias strength-log \
  -keyalg RSA -keysize 2048 -validity 10000
```

`keytool` will prompt for a store password and a key password (they can be
the same value). Write both down somewhere durable. Once Play App Signing
is accepted (§5.6) this keystore is the *upload* key — losing it is a
support-ticket reset, not a bricked listing — but before that first upload
it is the only identity the app has, so treat it like a house key anyway.

## 2. One-time per machine: point Gradle at it

`app/build.gradle.kts`'s `release` signing config reads four Gradle
properties and does nothing if they're absent (the build stays unsigned,
which is fine for local `assembleRelease`/CI verification — R8 still runs,
you just can't install or upload the result). Add them to
**`~/.gradle/gradle.properties`** — your per-user Gradle config, outside any
repo, never committed by definition:

```
STRENGTHLOG_RELEASE_STORE_FILE=/home/you/keystores/strength-log-release.jks
STRENGTHLOG_RELEASE_STORE_PASSWORD=...
STRENGTHLOG_RELEASE_KEY_ALIAS=strength-log
STRENGTHLOG_RELEASE_KEY_PASSWORD=...
```

Do **not** put these in the repo's `gradle.properties` (that file is
committed) or in `local.properties` (that's already spoken for — SDK path).
`~/.gradle/gradle.properties` is the standard place Android tooling expects
per-machine secrets like this to live.

## 3. Build

```
JAVA_HOME=/usr/lib/jvm/java-21-temurin-jdk ./gradlew :app:bundleRelease
```

Gradle 9.6.1 and AGP 9.2.1 need the Gradle daemon on JDK 21 (CI uses Temurin
21); the modules still compile to a JVM 17 target through toolchains.
`:wear:bundleRelease` builds the watch bundle the same way.

This produces a signed `.aab` at `app/build/outputs/bundle/release/` — the
format Play wants. `:app:assembleRelease` also works if you need a signed
`.apk` (e.g. to sideload the actual release build for the device smoke test
in step 4, instead of the debug-keystore build you've been using for day-to-
day testing).

Both tasks run R8 (`isMinifyEnabled = true`, `isShrinkResources = true`,
`app/proguard-rules.pro`). R8's runtime behavior (as opposed to
"did it build") can only be verified on a device, which is why step 4 below
exists.

## 3b. The baseline profile (optional, but it's what keeps the scroll smooth)

The release build compiles `app/src/release/generated/baselineProfiles/` AOT,
so the day screen's Compose call graph runs compiled from the first frame
instead of being interpreted while the lifter is already scrolling it (#156).
Nothing breaks without one — the app just JITs its way through the first few
hundred milliseconds of every cold start, which is where its jank history
comes from.

The profile is generated by driving the real app on a device or emulator, so
it is regenerated, not written:

```
./gradlew :app:generateReleaseBaselineProfile -PbaselineProfileGeneration=true
```

The flag is not optional: without it the two release variants the generator
needs stay switched off, so that every ordinary `./gradlew build` — CI's
included — doesn't pay for a profiling toolchain it never uses. The task
installs a non-minified release build, runs
`:baselineprofile`'s `BaselineProfileGenerator` against it, and writes the
result back into `app/src/release/generated/baselineProfiles/`. **Commit
that file.**

No hardware handy? Run the **Baseline profile** workflow from the Actions tab
(`.github/workflows/baseline-profile.yml`) and commit the artifact it uploads.

Regenerate after any real change to the startup path or the day screen's
scroll path; a stale profile is merely less useful, never wrong.

## 4. Device smoke test (R8 is on — do this before shipping)

R8 strips/renames anything it can prove is unreferenced, and reflection is
exactly the kind of reference it can't see. `proguard-rules.pro` has keep
rules for our `@Serializable` classes, and Room/Hilt/Compose/Health Connect
each bundle their own consumer rules, but "should be covered" isn't the same
as "verified on-device." Install the signed release build (not a debug
build — the whole point is exercising R8's output) and walk every
reflection-sensitive path once:

- **Wizard finish** — completes onboarding, writes the generated program to
  Room. Exercises kotlinx.serialization (`CardioSerialization`/
  `SetSerialization` TypeConverters) and Room/Hilt DI end to end.
- **Day logging** — log a set, mark it done, add/remove a set. Exercises
  the live Room-backed ViewModel wiring.
- **Backup export → restore** — export a full JSON backup, then restore it.
  Exercises `BackupDocument`'s kotlinx.serialization tree directly — this is
  the path most likely to silently break under R8 if a keep rule is missing
  (it'll fail loudly: either the export throws, or the restore reads back
  wrong/empty data).
- **CSV import** — import a Strong-style CSV, confirm an unmatched-exercise
  pattern, commit the import.
- **Health Connect publish** — connect Health Connect from the card in the Log
  screen, grant permissions, complete a day, confirm the session shows up in Health
  Connect (or another HC-reading app). Exercises the Health Connect client's
  AIDL-backed calls under R8.

If any of these behave differently than the debug build (crash, silently
empty data, a field that reads back as its default instead of what you
entered), that's a missing keep rule — file it before shipping, don't ship
around it.

## What's out of scope here

- (Historical: `:wear` used to be unminified and unsigned. It now shrinks
  with R8 and signs with the same four properties as `:app`, and §6's
  pipeline publishes it to its own Wear form-factor track.)
- Listing text, icon and feature graphic live in `play/listing/en-US/` and are
  pushed by the manual "Play store listing" workflow (`.github/workflows/play-listing.yml`,
  modes `inspect` and `upload`; the service account needs View app information
  (read-only) for inspect and Manage store presence for upload). The answers
  for the Console forms are in `docs/play-console-checklist.md`. Screenshots
  are rendered and published by the release workflow (§6).

## 5. Play Console: one-time setup (owner-only)

Use the browser for Play Console and Cloud Shell for the Google Cloud commands,
signed in as the owner. The publish pipeline (§6) only works after this is
done once.

1. **Developer account** — play.google.com/console, one-time $25.
2. **Decide free vs paid FIRST.** A free app can never become paid under the
   same applicationId — the decision is permanent at first publish.
   **Decided 2026-08-24: paid, $4.99 USD, with every international price set
   by hand to match rather than Play's auto-conversion.**
3. **Create the app** (`cloud.trotter.log.strength`). The Play API cannot
   create apps; the first AAB of each form factor is also easiest uploaded
   by hand here, after which the pipeline takes over.
4. **Store listing.** Title, short + full description, 512px icon, feature
   graphic, phone screenshots, and — because the wear bundle ships too —
   Wear OS screenshots (the Console gates the Wear form factor on them).
5. **App content declarations**:
   - *Privacy policy URL* — host `docs/privacy.md` somewhere public (GitHub
     Pages of this repo is fine) and paste the URL. Required regardless of
     the empty data-safety form because of the health permissions.
   - *Data safety* — copy the answers from `docs/play-data-safety.md`.
   - *Health apps declaration* — every Play app completes this form now;
     this one declares Health Connect read/write use (the manifest carries
     the permissions), which brings Play's Health Connect policy review:
     a privacy policy is mandatory and the declared use must match the
     manifest. Budget extra review time rather than counting on the
     ordinary turnaround.
   - Content rating questionnaire, ads declaration (none), target audience.
6. **Play App Signing** — accept it (Google holds the app signing key; the
   §1 keystore becomes the *upload* key, which is resettable if lost).
7. **Internal testing track** — create it and add tester emails (your own,
   at minimum). Testers opt in via the link the Console shows.
8. **Service account for the pipeline.** In Google Cloud, create a service
   account with no project-level roles and no key. The organization policy
   `iam.managed.disableServiceAccountKeyCreation` blocks keys, so both Play
   workflows use Workload Identity Federation. They can authenticate only
   from `main` or `v*` tags of `sjtrotter/strength-log`.

   In Cloud Shell, select the project that owns the service account. Set
   `PROJECT_NUMBER` to its numeric project number and `SA` to the service
   account's email, then enable the APIs and create the `github` pool and
   `strength-log` OIDC provider:

   ```sh
   PROJECT_NUMBER='your-project-number'
   SA='your-service-account@your-project.iam.gserviceaccount.com'
   gcloud services enable iamcredentials.googleapis.com sts.googleapis.com androidpublisher.googleapis.com
   gcloud iam workload-identity-pools create github --location=global --display-name=GitHub
   gcloud iam workload-identity-pools providers create-oidc strength-log --location=global --workload-identity-pool=github --issuer-uri=https://token.actions.githubusercontent.com --attribute-mapping=google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.ref=assertion.ref --attribute-condition="assertion.repository=='sjtrotter/strength-log' && (assertion.ref=='refs/heads/main' || assertion.ref.startsWith('refs/tags/v'))"
   gcloud iam service-accounts add-iam-policy-binding "$SA" --role=roles/iam.workloadIdentityUser --member="principalSet://iam.googleapis.com/projects/$PROJECT_NUMBER/locations/global/workloadIdentityPools/github/attribute.repository/sjtrotter/strength-log"
   ```

   For an existing provider, apply the same condition:

   ```sh
   gcloud iam workload-identity-pools providers update-oidc strength-log --location=global --workload-identity-pool=github --attribute-condition="assertion.repository=='sjtrotter/strength-log' && (assertion.ref=='refs/heads/main' || assertion.ref.startsWith('refs/tags/v'))"
   ```

   In Play Console → Users and permissions, invite the service account's
   email. Grant app-level permissions only for this app: **View app information
   (read-only)**, **Release apps to testing tracks**, and **Manage store presence**.
   Never grant Admin or production release permissions.

## 6. Releasing (.github/workflows/publish-internal.yml)

Push a version tag to publish release-signed phone and Wear bundles to
`internal` and `wear:internal`:

```sh
git tag v0.4.0 <commit on main> && git push origin v0.4.0
```

Or create a GitHub Release in the web UI that creates the tag. The tagged
commit must be on `main`; merges alone never publish. Tags must have the
form `vMAJOR.MINOR.PATCH`, with no leading zeros. Stay on 0.x until the
first production release, which is 1.0.0. A minor version is a feature
release; a patch is fixes only. Tags must only go up. Minor and patch must
each be at most 99. The lowest accepted tag is `v0.1.0`; Play already holds
codes up to 13 from earlier builds.

The version name is the tag without `v`. The phone version code is
`major*100000 + minor*1000 + patch*10`; the watch uses that code + 1:

| Tag | Phone code | Watch code |
|---|---|---|
| `v0.4.0` | 4000 | 4001 |
| `v1.0.0` | 100000 | 100001 |

The phone code must be at most 2099999990 (Play's maximum is 2100000000).
Devices never update to a lower code. A run that failed before either
upload can be re-run. Once an upload has reached Play, its version code is
used, so fix it with the next patch tag. Re-running only a failed release
job does not repeat the uploads.

After both uploads succeed, the release job creates the GitHub Release
with generated notes. A Release created by hand in the web UI keeps its
notes; the release job publishes it if it is still a draft and sets its prerelease status. Versions with
major 0 are marked as prereleases.

Each release also renders the store screenshots and attaches
`store-screenshots.zip` to the GitHub Release. While the repository variable
`PLAY_LISTING_AUTO_UPLOAD` is `true`, it replaces the phone and Wear screenshots
on the Play listing. The listing is public and shared by all tracks, so delete
the variable at launch. After that, run the "Play store listing" workflow in
`screenshots` mode with the release tag after promoting it to production.
If an upload fails because an update is in review, re-run the `listing` job later.

Enable automatic uploads before launch:

```sh
gh variable set PLAY_LISTING_AUTO_UPLOAD --body true
```

At launch, disable them:

```sh
gh variable delete PLAY_LISTING_AUTO_UPLOAD
```

Promote to production by hand in the Play Console; the service account
cannot release to production.

Protect tags with a GitHub tag ruleset targeting **All tags**, restricting
creation, update and deletion, with repository admins as bypass. A `v*`
pattern does not match `/`, so it would miss a tag like `v1/x`, which the
Google login still accepts. Anyone who can push a version tag can publish
to testers.

GitHub secrets it needs (Settings → Secrets and variables → Actions) — the
keystore travels as base64, decoded into the runner's temp dir and scrubbed
after; no signing material ever exists in the workspace or repo:

| Secret | Value |
|---|---|
| `UPLOAD_KEYSTORE_BASE64` | `base64 -w0 ~/keystores/strength-log-release.jks` |
| `UPLOAD_STORE_PASSWORD` | the §1 store password |
| `UPLOAD_KEY_ALIAS` | `strength-log` |
| `UPLOAD_KEY_PASSWORD` | the §1 key password |

Repository variables in the same settings:

| Variable | Value |
|---|---|
| `PLAY_WIF_PROVIDER` | `projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/github/providers/strength-log` (replace `PROJECT_NUMBER`) |
| `PLAY_SERVICE_ACCOUNT` | the §5.8 service-account email |

The workflow refuses to run (with a pointed error) when required secrets or
variables are absent, so a fork or a fresh clone can't half-publish anything.
